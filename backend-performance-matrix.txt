Notes on the ❌s that look surprising
Bid find/create/update all ❌ for Authenticated — this is intentional, not an oversight. bid.create/update/delete are explicitly overridden in the controller to reject with methodNotAllowed (see the earlier custom-controllers doc) — bids can only be created through bid.place, which enforces wallet balance, currency conversion, and extension-window logic that the raw REST create would bypass entirely. Toggling create on in the permissions panel wouldn't actually let anyone bypass this since the controller itself refuses — but leave it off anyway so the admin panel doesn't advertise a route that always 405s.
Wallet/Transaction find/findOne ❌ for the same reason — a raw GET /wallets with no filter would leak every user's balance to any authenticated user. myWallet/myTransactions scope to ctx.state.user.id internally, which the generic find action can't do without a forced filter Strapi's permission UI doesn't support out of the box.
OTP Verification all ❌ — send/resend/verify are the only entry points, and those are Public (no login yet at OTP time, obviously). An authenticated user has no legitimate reason to touch this content type directly.
Users update — own record only — this is Strapi's default behavior via /users/:id once update is checked; there's no built-in "own record only" toggle, so if you check this on, also confirm your users-permissions config restricts update to the record matching ctx.state.user.id (default users-permissions behavior does this already for non-admin JWTs — just verify it hasn't been loosened).
What's deliberately absent from both tables

Admn Setting has zero permissions on either role — it's only ever read server-side via resolveSettingsForCountry, never exposed directly over REST. If you later want an admin-facing settings page in your own admin panel (not Strapi's), that should go through the Strapi admin API (different auth entirely — admin JWT, not users-permissions), not this matrix.
